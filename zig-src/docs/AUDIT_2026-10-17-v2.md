## 1. 背景：这份 Zig 改造是什么

### 1.1 目标与硬约束

- **目标**：把 OpenList 兼容服务塞进**中兴 F4610U 光猫**（aarch64 / musl / squashfs / 内存与存储都极小）。
- **体积动机**：Go 版全量驱动二进制 **45,154,464 B**（README:17，不含前端）；含 `//go:embed` 前端的生产构建约 **88 MB**（设备实例实测 88.5 MB），前端资源本身约 **20 MB**（STATUS §22.1:1376）。Zig 版 **约 1.14–1.21 MB**。前端不内嵌是“项目存在意义”（`STATUS §22.1`）。
- **构建**：本机无 Zig 工具链，一律走打包机 `10.0.0.4`（`tools/build_remote.py`：上传 → `zig build test` → `aarch64-linux-musl` 交叉编译 → 取回）；真机测试只在 `/tmp/olz`，绝不碰生产实例。

### 1.2 与 Go 对应的架构决策（理解差异的前提）

| 维度 | Go 上游 | Zig 版 | 后果 |
|---|---|---|---|
| 存储 | SQLite `data.db` | 单文件 `config.json`（Go 键 + `zig.*` 块） | 无多用户/无 DB 事务；配置写回需自己保证原子性 |
| 用户 | 用户表、多用户、角色/权限 | **单管理员**（`zig.admin_*` 四键），`permission` 默认 `0x71FF` | 分享/SSH 公钥/WebAuthn/2FA/LDAP/SSO 全部无意义 |
| 前端 | `//go:embed` 内嵌 | CDN / `dist_dir` / 内置占位页三选一 | 启动强依赖 CDN（`CdnIndexFetchFailed` 直接退出） |
| HTTP 服务端 | `net/http` + gin | 手写 HTTP/1.1（`http.zig`，`std.Io.net`） | 每请求一个 **ArenaAllocator**（`http.zig:622-626`）——这是 H1/H2 类所有权问题的土壤 |
| HTTP 客户端 | 每请求独立 + 连接池 | 每驱动一个 `Client`，**每个 Client 一把全局锁**（`client.zig:159,369`） | 同一驱动内请求串行；并发靠"每 worker 一个 Client"（pan123/itvsh 这么做，189pc 没做） |
| 对象模型 | `model.Object` 带 `ID` | `model.Obj` **无 ID**（只有 `name/sign/priv`，`model.zig:70-89`） | 189/189pc 每次操作按路径逐段翻页找 ID；深路径/大目录多打请求 |
| 驱动 | 80+ 驱动 | 11 个实现 / 12 个注册项，**编译期白名单** `-Ddrivers=` | 未注册驱动导入配置后 init 失败（Baidu/Onedrive 属预期） |
| 配置迁移 | — | `import_go_config.py` 直读 Go 备份；`addition` 仍是字符串 | 密码哈希不迁移（Go `json:"-"`），首次启动需 `admin set` 或 setup |

## 3. P0 明细

### H5. pan123 批量上传 refetch 竞态（维持高危，真内存损坏）

- **位置**：`pan123.zig:930-938`（`refetch`）、`:967`（无锁读）、`:944/:954`（worker arena deinit/reset）。
- **机理**：预签名 URL 过期（403）时，某个 worker 调 `refetch(a)`，`a` 是**它自己的 arena**；`json.parse(a, body)` 的结果被写进 `state.urls`，随后该 worker 在每片之后 `arena.reset(.retain_capacity)`。Zig std 的 `reset` 明确会**保留缓冲并复用**（`end_index=0`），其他 worker 仍无锁读 `state.urls` ⇒ 读到被覆盖的 keys/vals 指针（撕裂读/段错误/发错 URL）。
- **Go 对照**：`drivers/123/upload.go:151` 用 `singleflight.AnyGroup.Do("Pan123.newUpload_%p")` 把换批收敛成一次，返回值生命周期由 Go GC 保证，不存在该问题。
- **修复**：refetch 的解析结果放进 `BatchState` 自有的请求级 allocator（如 `state.alloc` 或单独 arena，生命周期到整批结束），`urls` 读写都持 `mu`；补多 worker + 注入 403 的并发测试。
- **置信度**：高（两侧代码 + std 语义均已核对）。

### H1/H2. 189 个人云 / 家庭云 list 的所有权 bug（v2 降级为"潜伏但必修"）

- **位置**：`cloud189.zig:736-768`（name/thumb）、`cloud189pc.zig:1487-1535`（thumb/hash_value）。
- **机理**：`getFiles` 用内层 `ArenaAllocator.init(alloc)` 解析分页 JSON，输出数组用 `alloc`（= `ctx.alloc` = 请求级 arena）。函数返回时内层 arena `deinit()`，其 chunk 通过 `child_allocator.rawFree` 归还给**请求 arena**；而 arena 的 `free` 只在"释放的是最近一次分配"时回退 `end_index`，否则 no-op。
  - 常见路径：最后一次 `out.append`（请求 arena 分配）晚于最后一次内层 arena 分配 ⇒ deinit 时不是"最近一次分配" ⇒ no-op ⇒ 字符串在请求结束前仍然有效。**这解释了真机 e2e 全绿**。
  - 边界：最后一页没有追加（如仅 folders 且列表为空？或 toOwned 无新分配）时，deinit 可能回退请求 arena，随后响应 JSON 缓冲区的分配会覆盖名字 ⇒ 乱码。
  - 未来风险：任何用 GPA/长生命周期分配器调用 `getFiles` 的路径（后台扫描、缓存预热）会立即变成真实 UAF。
- **Go 对照**：`drivers/189/util.go:179-224` 的 `getFiles` 直接构造 `model.Object`（Go 堆 + GC），无生命周期问题；且 Go 对象带 `ID`，Zig 不带（见 §1.2）。
- **修复**：与 `cloud189pc.zig:1509` 一致，把 `name`/`thumb`（以及 hash_value）`dupe` 进 `alloc`；或让输出与解析共用同一 arena。补"返回后覆写内存再断言"的单测。
- **置信度**：高（代码 + std 语义 + 调用链均已核对）。

### H7. cookiejar 反序列化 panic

- **位置**：`cookiejar.zig:400-401`：`item.getPath("Secure").?.asBool() orelse false`。
- **触发**：`addition` 里的 cookie blob 缺 `Secure`/`HttpOnly` 键（手改配置、旧版/第三方工具生成）。itvsh 每次 init/relogin 都走 `fromJson` ⇒ **启动即崩**，只能改配置文件恢复。
- **为何不是"所有 blob 都崩"**：本版序列化（`:352-354`）总写这两个键。
- **修复**：改成 `(item.getPath("Secure")) |v| v.asBool() orelse false else false`；补最小 blob 反序列化测试。
- **置信度**：高。

## 4. P1 明细

### H3. wopan 刷新后重放旧密文（自愈失效）

- **位置**：`wopan.zig:439-442`。`refreshToken()` 成功后用**旧的 `param_b64`** 递归 `post`；wohome 通道 AES key = `accessToken[:16]`，刷新后 key 已变 ⇒ 服务端解密失败（9002）。
- **Go/SDK 对照**：SDK 每次请求都 `NewBody(channel, param, other)` 重新加密（`wopan-sdk-request.go:19,47`）；Zig 的 `post` 接收的是**已加密的 param_b64**，因此重试必须重新构造。
- **影响**：会话中途失效时，刷新成功但重试失败 ⇒ 挂载进入 errored，重启后恢复（新 token 已落盘）。
- **修复**：`post` 改为接收明文 param + 通道，内部加密；或重试前用新 token 重新 `encryptParam`。

### M1. `sign_all` 默认值与 Go 相反

- Zig `config.zig:542`：`boolean(..., false)`；Go `internal/bootstrap/data/setting.go:171`：默认 `"true"`。
- 影响：全新部署下 Go 默认所有下载需签名，Zig 默认公开可下载。用户现有备份是 `true`，不受影响；**新部署安全姿态相反**。
- 修复：默认改 true（并在文档注明迁移时以配置文件为准）。

### M11. 登录错误码与防爆破

- Zig `api.zig:1025-1043`：用户名/密码错误统一 **400** `wrong username or password`，无重试计数。
- Go `server/handles/auth.go:47-64`：**401** `InvalidUsernameOrPassword`，`LoginCache` 同 IP ≥5 次锁 5 分钟回 **429** `TooManyAttempts`。
- 影响：第三方客户端按 401 判断"凭据错误"的逻辑会误判；暴露在公网时无暴力破解防护。
- 修复：错误码改 401；加 IP 计数（内存 map + 过期）。

### H6. 响应头/重定向 CRLF 注入（纵深防御）

- `http.zig:975` 原样打印头值；`http.zig:393-397` `redirect` 直接 `set("Location", location)`；`api.zig:3532` 的目标来自驱动 `link()`（上游 JSON）。
- 前提：上游响应体含 CRLF（恶意/被污染上游、WAF 回显页）。Go `net/http` 会拒绝非法头值。
- 修复：`Response.set`/`redirect` 统一拒绝或剔除 `\r\n\0`。

### M2. 115 link 丢弃 header

- `pan115.zig:697` 返回 `.header = &.{}`；Go `drivers/115/driver.go:77` 挂 `downloadInfo.Header`（`DownloadWithUA` 生成，含 UA 与 Set-Cookie；115 直链按 UA 授权）。
- 影响：代理下载可能 403。**注意**：该 SDK 不在本仓库，结论依赖外部实现；真机 115 下载未单独回归（§36A.2 只验证了 mkdir）。
- 修复：把 header 透传到 `model.Link`（`model.Link` 已有 header 字段）。

### M9. `fs/get` 缺 3 个字段，`fs/list` 缺 1 个

- Go `FsGetResp`（`server/handles/fsread.go:255-262`）= `ObjResp`（含 `thumb`、`hashinfo`、`hash_info`）+ `raw_url/readme/header/provider/related`。
- Zig `api.zig:1296-1333` 缺 `thumb`、`hashinfo`、`hash_info`；`writeObj`（`:3722-3738`）list 项有 `thumb` 与 `hash_info:null`，缺 `hashinfo` 字符串。
- 影响：前端详情/预览的缩略图与哈希信息为空。

### M12. `fs/dirs` 形状与语义均不符

- Go `FsDirs`（`fsread.go:129-179`）：列出**请求路径的子目录**，返回**裸数组** `[{name,modified}]`。
- Zig `api.zig:1136-1159`：列出**挂载点**，返回 `data:{content:[{name,path,driver,label,order}]}`。
- 影响：第三方/脚本按 Go 契约调用会拿错数据。**前端是否调用未确认**（仓库内 bundle 未检出 `fs/dirs`，可能是旧快照/动态拼接），故列 P1 而非 P0。

### M16. `putZig` 与 `save()` 的配置写回竞态

## 5. P2 / P3 明细（含 v2 降级项）

### M6. itvsh 分片重试范围窄（中）

## 8. 方法与局限

- 本轮**未编译、未运行、未上真机**；结论为静态源码级（Go 与 Zig 双侧逐行核对）。

## 9. 结论

v2 的核心判断：**这个 Zig 版在"协议对齐"上做得相当扎实**（密码哈希/签名/JWT/信封/驱动名/WebDAV 均逐字节或逐头对齐，12/12 驱动真机覆盖），**主要风险集中在内存所有权与少数契约细节**。P0 只有 3 项（H5、H1/H2、H7），其中 H1/H2 在当前请求级 arena 架构下是"潜伏"而非"必现"——但它们是所有权契约问题，一旦调用方换成 GPA 或跨请求复用就会立即变成真实 UAF，仍应尽快修。P1 的 8 项是功能/安全面的实际差异，建议按 §2 的顺序处理。
