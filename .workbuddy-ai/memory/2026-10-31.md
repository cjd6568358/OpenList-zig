## 新增 `.github/workflows/proxy_download.yml`（代理下载取件 workflow）

- 目的：给一个下载链接，在 runner 上拉下来 → 上传到本次 run 的 artifacts；支持**代理前缀列表**（`https://ghfast.top/` 这类），按序尝试、全失败才报错。
- 输入：`url`（必填）、`proxy_prefixes`（默认 `https://ghfast.top/,direct`，`direct`/`-` 表示直连，前缀末尾斜杠自动补）、`filename`、`sha256`、`artifact_name`。
- 三个 step：`Resolve target filename`（python3 urlparse 解 %xx + 白名单字符清洗）→ `Download`（curl `-fL --retry 3 --retry-all-errors`，逐候选 `::group::`，成功判据 = 非空 + 非 HTML 错误页 + 可选 sha256）→ `Collect artifacts`（`<file>` + `<file>.sha256` + `manifest.txt`，另写 job summary 表）。
- 与仓库约定对齐：`actions/upload-artifact` 沿用同一 pin `043fb46d…`（v7）；不 checkout；`permissions: contents: read`；URL 一律经 env 传进 shell 不插值。
- 本地验证（假 curl 桩 + `bash -n`）：7 个场景通过 —— 代理优先 / 前缀无斜杠 / 代理失败回退直连 / 留空直连 / HTML 错误页全败 / sha256 不符 / sha256 正确；另测文件名解析 8 例（`%xx` 解码、query 剥离、`../../etc/passwd` → `passwd`、空 URL 拒跑）。
- 修过一处：`EXPECTED` 未定义时 `set -u` 报 unbound variable（本地复跑才触发），已加 `${VAR:-}` 兜底。
- 顺带把 `MEMORY.md` 从 15.5 KB 压到 13.2 KB（8848 字符），**修掉「分片上传」自相矛盾的记录**：STATUS §55 的 `multipart_enabled=false` 已作废，10-30 晚起 multipart 全实现、`multipart_enabled=true`。

## 更正：代理前缀是指「产物下载链接」，不是取件时走代理

- 用户澄清：**「代理」= 生成出来的产物下载链接要能套代理前缀**（贴到本机浏览器/curl 走 ghfast），不是 workflow 自己下载时走代理。原先的「候选前缀逐个试」实现是理解错方向，已整体重写。
- **关键约束（决定了产物必须发 Release）**：artifacts 的下载链接是**鉴权**的（`/actions/runs/<id>/artifacts/<aid>` 匿名访问跳登录页），前缀代理拿不到 cookie ⇒ 给 artifact 链接套前缀无效。能套前缀的只有公开链接 = Release 资产 `/releases/download/<tag>/<file>`。
- 新形态（6 step）：`Resolve target filename` → `Download`（**直连**，只保留 `--retry`/非空/非 HTML/可选 sha256）→ `Collect artifacts` → `Upload workflow artifacts` → `Publish Release asset`（`publish_release` 默认 true，tag 留空则 `dl-<UTC 时间戳>`，顺带挂 `.sha256`）→ `Render download links`。
- `proxy_prefixes` 语义改为**只渲染链接**：每个前缀输出一行 `https://ghfast.top/<release 资产 URL>`；artifact 那行显式标注「需登录，代理无效」且**不渲染前缀**。job outputs：`artifact_url` / `release_url` / `proxied_release_url`（无前缀时为空）。
- `permissions` 改 `contents: write`（要发 Release）。本地用桩验证 4 种组合（有/无 release × 有/无前缀）summary 与 outputs 正确，5 个 run 块全过 `bash -n`。

## 坑：不 checkout 时 `gh` 报 `fatal: not a git repository`

- 现象：`Publish Release asset` 步骤 0–1s 就失败，`failed to run git: fatal: not a git repository (or any of the parent directories): .git`。
- 原因：`gh` 靠 `git remote` 推断当前仓库；workflow 为省 clone 没 checkout ⇒ 无 `.git`。
- **只给 `GH_REPO` 不够**（实测仍失败，gh 在部分子命令里照样摸 git）。最终解法：加 `actions/checkout@3d3c42e…`（`fetch-depth: 1`），**只要 `.git` 不要代码**；`GH_REPO` 保留作双保险。
- 顺带：发布步骤加 `continue-on-error: true` + `trap ... ERR` 打 warning，并在开头 `echo` gh 版本 / `GH_REPO` / `git remote get-url origin` 做环境自检。
- 教训：**GitHub 的 "Re-run all jobs" 复用原 commit**，改了 workflow 要重新 dispatch，否则看到的还是旧代码的报错。

## 分片回退路径容量闸 + 1 GiB 真机验收（下午）

- **加闸**：`App.mp_max_bytes`（= `zig.max_upload_mb`，main.zig 接线）。`handleMultipartInit` 的回退分支超限 ⇒ 会话不建 + **真实 HTTP 413**（中文信封）；直传分支不受影响。动机：§56.1 的闸只拦 `fs/put`/WebDAV PUT，`multipart/init` 回退路径会整份落 tmpfs，1 GB 必然 ENOSPC/OOM。

- **真机**（/tmp/olz，隔离配置只留 /ecloud_self + Local）：回退 200 MiB ⇒ 413；回退 10 MiB ⇒ 200；直传 200 MiB ⇒ 200；**1 GiB 直传成功**（103 片 × 10 MiB，2950 s ≈ 0.35 MiB/s 上行瓶颈，RSS 峰值 23.2 MB，/tmp 全程 5.6 MB，size + 首尾 1 MiB MD5 一致）。测试文件已从网盘删除，实例与 /tmp/olz 清理，生产 15244 未受影响。
