## 更正：代理前缀是指「产物下载链接」，不是取件时走代理

- 用户澄清：**「代理」= 生成出来的产物下载链接要能套代理前缀**（贴到本机浏览器/curl 走 ghfast），不是 workflow 自己下载时走代理。原先的「候选前缀逐个试」实现是理解错方向，已整体重写。
- **关键约束（决定了产物必须发 Release）**：artifacts 的下载链接是**鉴权**的（`/actions/runs/<id>/artifacts/<aid>` 匿名访问跳登录页），前缀代理拿不到 cookie ⇒ 给 artifact 链接套前缀无效。能套前缀的只有公开链接 = Release 资产 `/releases/download/<tag>/<file>`。
- 新形态（6 step）：`Resolve target filename` → `Download`（**直连**，只保留 `--retry`/非空/非 HTML/可选 sha256）→ `Collect artifacts` → `Upload workflow artifacts` → `Publish Release asset`（`publish_release` 默认 true，tag 留空则 `dl-<UTC 时间戳>`，顺带挂 `.sha256`）→ `Render download links`。
- `proxy_prefixes` 语义改为**只渲染链接**：每个前缀输出一行 `https://ghfast.top/<release 资产 URL>`；artifact 那行显式标注「需登录，代理无效」且**不渲染前缀**。job outputs：`artifact_url` / `release_url` / `proxied_release_url`（无前缀时为空）。

## 坑：不 checkout 时 `gh` 报 `fatal: not a git repository`

- 现象：`Publish Release asset` 步骤 0–1s 就失败，`failed to run git: fatal: not a git repository (or any of the parent directories): .git`。
- 原因：`gh` 靠 `git remote` 推断当前仓库；workflow 为省 clone 没 checkout ⇒ 无 `.git`。
- **只给 `GH_REPO` 不够**（实测仍失败，gh 在部分子命令里照样摸 git）。最终解法：加 `actions/checkout@3d3c42e…`（`fetch-depth: 1`），**只要 `.git` 不要代码**；`GH_REPO` 保留作双保险。
- 顺带：发布步骤加 `continue-on-error: true` + `trap ... ERR` 打 warning，并在开头 `echo` gh 版本 / `GH_REPO` / `git remote get-url origin` 做环境自检。
- 教训：**GitHub 的 "Re-run all jobs" 复用原 commit**，改了 workflow 要重新 dispatch，否则看到的还是旧代码的报错。

## SFTP handler 层落地（同日晚）

- `src/sftp/handler.zig`（1488 行含 12 test）：`PacketType` → `driver.Driver` vtable 分发。
- **★ 架构决定：两个窄接口隔离依赖**，不直接拿 `*api.App`：
  - `Resolver`（路径 → `Target{driver, rel, mount_path}`），生产包 `App.resolve`（最长前缀匹配），测试包内存驱动；
  - `Fetcher`（link + offset + len → bytes），生产包 `client.zig` Range，测试包内存切片。
  - 收益：分发逻辑全可纯单测（不起服务/不联网/不需凭据）。这是本模块最重要的设计选择。
- **已支持**：INIT / REALPATH / STAT / LSTAT / FSTAT / OPENDIR / READDIR（64 条一页，末尾 `eof`）/ MKDIR / RMDIR / REMOVE / RENAME / OPEN(只读) / READ(1 MiB 窗口缓存) / CLOSE / SETSTAT。
- **明确不支持并回 `op_unsupported`**（不静默）：OPEN 写模式 + WRITE（需 pwrite 进 temp_dir 稀疏文件 + CLOSE 时整份 put + 容量闸）、SETSTAT 的 size（截断是真数据操作）、READLINK/SYMLINK/EXTENDED。
- **句柄状态挂 `session.Handle.extra` + `release` 回调**：会话层不 import model/driver，保持零依赖；closeHandle/reset/deinit 三处都调 release。
- **OPEN 必须深拷贝 link**（url/text 活在请求 arena，句柄跨请求存活 ⇒ 否则悬垂）。
- **RENAME 跨目录 = move + rename 两步**：vtable 的 `move` 第二参数是**目标目录**，所以解析目标要用 `dirname(new_path)` 而非 new_path（否则驱动拼出 `/dst/c.txt/a.txt`）；改名失败时源已移动，如实报错。
- **★ 真 bug：`std.fs.path.join` 不能用于虚拟路径** —— 它按宿主分隔符拼，Windows 上产出 `/dst\a.txt`，虚拟路径必须永远 `/`。自写 12 行 `joinVirtual`。`dirname`/`basename` 安全（同时识别两种分隔符）。单测在 Windows 上先红才暴露。

## SSH-2 传输层落地 + OpenSSH 实测（同日晚）

- **`src/sftp/ssh.zig`（~800 行，7 test）**：版本交换、KEXINIT、`curve25519-sha256`（RFC 8731）、`ssh-ed25519` host key、二进制包协议、`aes128-ctr`+`hmac-sha2-256`、NEWKEYS 六方向密钥派生。**只宣告一套算法**（矩阵越小出错越少），协商失败明确断连不降级。
- **★ MAC 必须覆盖明文包**（RFC 4253 §6.4，含 4 字节长度字段），先加密再算 MAC 必然 `BadMac`。
- **CTR 要支持分段**：SSH 的长度字段也加密 ⇒ 必须能「先解 4 字节、再解剩余」共用同一条 keystream（`CtrCipher` 自己维护 counter + pos）。有单测对比一次性 vs 分段。
- **host key 持久化** `data/ssh_host_ed25519_key`（32B seed）：每次重启换密钥会让所有客户端弹 known_hosts 警告。
- **★ OpenSSH 10.3 实测决定性通过**：`kex: curve25519-sha256` / `host key: ssh-ed25519` / `aes128-ctr+hmac-sha2-256` / **客户端打印 SHA256 指纹（验签通过）** / `service_accept: ssh-userauth`（**成功解密我们的包**）/ 无 `Corrupted MAC` / 最后 `SSH2_MSG_UNIMPLEMENTED for 4`（认证未实现的预期表现）。
- **4 个 0.17 API 坑**：① `**` 数组重复运算符**已移除**（`[_]u8{0} ** 64` 报错）⇒ `@memset` helper；② `std.crypto.core.aes.AesEncryptCtx` 是**泛型**，要写 `AesEncryptCtx(Aes128)`；③ `Dir.makePath` → `Dir.createDirPath`；④ **`Buf.toOwned()` 又漏一次**（`errdefer` → 成功路径泄漏），「临时 Buf 一律 `defer`」要成条件反射。
- **体积**：1,889,792 → **1,915,904 B / `b29afc1d`**，SSH 层只 +26,112 B（crypto 全来自 std，零外部依赖）。

## 认证接真校验（同日晚，替换临时后门）

- **删掉 `acceptUnverified()`**，`channel.zig` 改为 `Auth` 接口（`verifyFn` 回调）：channel 只问「过没过」，不知道 `twoHashPwd` —— 口令哈希形态属于账户层，SSH 与 HTTP 必须同一套实现否则漂移。
- **`api.zig` 新增 `authThrottleAllow/Failure/Success`**，包住原 `login_throttle`（M11，对齐 Go `LoginCache`：5 次失败锁 5 分钟）。**SSH 与 HTTP 共用同一份计数**——换协议不能绕过限速；副作用是 SSH 爆破会顺带锁 HTTP 登录 5 分钟（单管理员可接受，Go 同款）。
- **`sftp_wire.sshVerify`**：admin_hash 空 ⇒ 拒；throttle 不允许 ⇒ 拒（**连哈希都不算**）；用户名不等 ⇒ fail+拒；`twoHashPwd(pw, admin_salt)` 不等 ⇒ fail+拒；全过 ⇒ success 清零。对外**不区分**用户名错/口令错。
- **`none` 方法永远不通过**（放行它 = 无认证登录）；客户端收到 FAILURE 会自动改试 password。
- **★ 锁定期间必须打日志**：`WARN ssh: auth refused — account locked after too many failed attempts`。没有它，用户输入正确口令也登不上却毫无线索 —— 「正确口令登不上」最典型的误诊来源。
- **实测（OpenSSH sftp）**：错口令 ⇒ Permission denied + 服务端 WARN；对口令 ⇒ 登录成功、ls/get 正常、内容逐字节一致；**连续 5 次错后即使口令正确也被锁**并打上述 WARN。
- **⚠ 计数 key 仍是全局而非按 IP**（`std.Io.net.Stream` 不暴露对端地址，与 HTTP 登录同一限制）⇒ 任何人可锁住管理员 5 分钟。将来拿到 IP 必须用**纯 IP 不带端口**。
- **体积**：1,922,560 → **1,923,584 B / `3461e7cd`**（认证只 +1,024 B，零新依赖）。单测 518 pass + 3 skip。
- **剩余**：① 失败计数按 IP ② 写路径 ③ `sftp` 配置段 ④ WinSCP/FileZilla/rclone + 删 `--sftp-plain`。

## 写路径落地（同日晚）

- **桥接方式**：`OPEN(write|creat|trunc)` 在 `temp_dir` 建空文件 → `WRITE` 按 offset pwrite → `CLOSE` 把 temp 包成 `model.Source` 一次 `driver.put`。
- **`FileState` 改成 `union(enum) { read, write }`**（原来是 struct）：读句柄有 link+缓存、写句柄有 temp 文件，用 union 让「读句柄当写句柄用」在编译期暴露。
- **容量闸**复用 `App.mp_max_bytes`（=`zig.max_upload_mb`），与 `fs/put`/分片回退同一笔账。
- **断点续传不支持**：`write` 无 `trunc` 且目标存在 ⇒ `op_unsupported`（要先下载现有内容才能续写）。
- **★ bug 1：`CreateFileOptions.read` 默认 false（只写）** ⇒ temp 文件 `readPositionalAll` 得 `AccessDenied`，症状是 put 显示 Uploading 后 `close remote: Permission denied`。加 `.read = true`。
- **★ bug 2（危险）：WRITE 失败后客户端**仍发 CLOSE**，无条件 put ⇒ 截断文件被当完整文件上传**。实测 9MiB 超 8MiB 闸，磁盘留下正好 8,388,608 B 的 `over.bin`（若目标已有文件还会被覆盖）。修法：`WriteState.failed` 标志，任何写失败置位，CLOSE 见到就删 temp + 回 failure。**「闸拦下数据却留截断文件」比不设闸更糟**，这类 bug 只在「中途失败 + 客户端仍提交」时出现，正常路径测不到。
- **实测**：29B / 1MiB（MD5 一致，跨多 WRITE 块）/ 9MiB 超限（write+close 双 Failure、磁盘无残留、temp 零残留）；上传后 temp 目录 0 文件。
- **体积**：1,923,584 → **1,930,240 B / `95a4034a`**（写路径 +6,656 B）。单测 518 pass + 3 skip。
- **剩余**：① 失败计数按 IP ② 断点续传 ③ `sftp` 配置段 ④ WinSCP/FileZilla/rclone + 删 `--sftp-plain`。

## 复核（同日晚，用户点名三处）

- **★P0 `channel.zig`：未认证也能开 channel。** `Conn.authenticated` 只被赋值（onUserauth 成功）、**从没被检查**，`onChannelOpen` 没有任何闸门 ⇒ KEX 完直接发 `CHANNEL_OPEN` + `subsystem sftp` 就能读写全部挂载，认证形同虚设。修法：`onChannelOpen` 开头 `if (!self.authenticated) return self.openFailure(a, sender, 1, "authentication required");`，`onChannelRequest`/`onChannelData` 同样加一道。
- **P1 `main.zig`：sftp 分支的 4 个 `return` 都在 `server.run()` 之前** ⇒ `sftp.port` 非法或线程 spawn 失败时 HTTP 服务**根本不启动**（配置文件写错一个端口，整个程序哑掉）。应改成记 err 后跳过 SFTP 继续跑。顺带发现同函数第 249 行 `buildMountsWorker` 同步兜底分支末尾的 `return;` 是同样毛病（既有代码）。
- **P1 `config.zig`：`sftp.port` 恒压过 `listen`。** DEFAULT_CONFIG 把 `"port": 2022` 写进了 config.json，而 `int(getPath("sftp.port"), cfg.sftp_port)` 只要键存在就生效 ⇒ 文档声明的「address+port > listen」实际反了：只写 `listen:"127.0.0.1:15402"` 的用户会被 2022 覆盖。修法：listen 只填补**未显式给出**的字段（`address`/`port` 各自判断键是否存在）。
- **P1 `handler.zig openForWrite`：`createFile` 之后没有 errdefer 兜 `f`。** `c.alloc.create(FileState)`、`vpath` 的 dupe、`p` 的 dupe 三处都可能失败，任一处失败 ⇒ fd 泄漏 + temp 文件残留磁盘（tmpfs = 吃 RAM）。另：`createFile` 的 catch 分支里先 `free(tmp_path)` 再 `try writeStatus`，后者 OOM 时 errdefer 会二次 free。建议把两次 `dupe` 和 `create` 都提到 `createFile` **之前**（只留 addHandle 失败一条路径，由 `FileState.release` 收尾）。
- **P2 allocator 不匹配**：`FileState` / `DirState` 用 `c.alloc` 创建，release 回调拿到的却是 `sess.alloc`（生产里两者都是 `rt.gpa()` 所以没炸）。建议把 alloc 存进状态结构体，release 内部用它。
- **P2 文档过期**：`channel.zig` 文件头仍写「放行任意口令 / TODO(auth) / 只绑 127.0.0.1」，`main.zig` USAGE 写「(auth pending)」，`sftp_wire.zig` 头写「SSH 传输层还没写」——都已与代码相反，会误导下一次改动。
- **P3**：sshVerify 用 `std.mem.eql` 比哈希（HTTP 路径用 `ctEqual`），建议统一；`parseListen` 遇到裸 IPv6（`::1`）会切成 host=`::`、port=1；客户端 rekey（`KEXINIT`）在 `dispatch` 里只回 UNIMPLEMENTED，长传输（OpenSSH 约 1GB/1h）会断，建议记进 TODO。
- **A–F 六方向核对无误**：A=IV_c2s B=IV_s2c C=Enc_c2s D=Enc_s2c E=MAC_c2s F=MAC_s2c；`session_id = t.session_id orelse h_hash`（仅首次 KEX 取 H）；H 的串接顺序 V_C‖V_S‖I_C‖I_S‖K_S‖Q_C‖Q_S‖K 与 RFC 8731 一致；MAC 覆盖 seq‖明文包（含长度字段）且在加密前计算；CTR 计数器大端 +1 正确。
- **窗口取舍结论**：可接受但不建议留。窗口不足时同步读包等 `WINDOW_ADJUST`（有界次数）只需十几行，比赌客户端宽容更划算。
