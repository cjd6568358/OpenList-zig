## SFTP：客户端 rekey + 第二个客户端实现（PuTTY）+ 两处收尾缺陷

接着 10-31 的 SFTP 收尾，做掉 TODO 里剩的 `TODO(rekey)` 与「互通待测」。

### 1. 客户端主动重协商（rekey）

- `ssh.kex` 拆成 `kexInner(t, host_key, alloc, pending_client_kexinit)`：
  `kex` 传 null（首次），`rekey` 传消息循环已读到的那份 KEXINIT。
- `channel.Conn` 新增 `host_key` 字段（`Conn.init` 多一个参数），
  `dispatch` 与 `waitForWindow` 两处都接 `MSG_KEXINIT → onRekey(p)`。
- 三个必须对的点：`session_id` 沿用首次 H（§7.2）；`seq_in/seq_out` 不重置
  （§7.3）；**重协商用连接级 allocator 而不是循环的 arena**（kex 会把双方
  KEXINIT dup 进 Transport，下次还要用；arena 下一轮就释放 ⇒ 悬垂）。
  连做两次 rekey 才能抓到这条。
- 验证：paramiko `Transport.renegotiate_keys()` 连做两次，之后 300 KiB get
  仍逐字节一致。

### 2. `readPacket` 的返回值不能 `free`

- 返回的是 `body[1..len-padlen]`（分配起点 +5、长度不同），直接 `a.free(p)`
  会被 `SafeAllocator` 判成非法释放 **panic**。
- 新增 `Transport.readPacketOwned` → `OwnedPacket{raw, payload}`，
  `deinit` 释放 `raw`；`readPacket` 变成薄包装（arena 调用方不用管）。
  `readKexPacket` 返回 `OwnedPacket`，KEX 三处读包点各 `defer deinit`。
  顺带补上「KEX 期间跳过 IGNORE/DEBUG/UNIMPLEMENTED、DISCONNECT 当即断开」。

### 3. 协商失败发 DISCONNECT（不再静默关 socket）

`checkKexInit` 失败 → `Transport.rejectKex` 发 §11.1 的 `DISCONNECT`：
算法不匹配 = 3（描述里写清支持什么），KEXINIT 解析失败 = 2。
原因码常量放在 ssh.zig 顶部（`DISCONNECT_PROTOCOL_ERROR` 等）。

### 4. ★ 收尾：收到 `CHANNEL_EOF` 必须由服务端回 `EOF` + `CLOSE`

**PuTTY 的 pscp 传完只发一个 EOF 就等服务端关**（RFC 4254 §5.3：EOF 不要求
回应，结束靠 CLOSE）。原来 `CHANNEL_CLOSE => return error.ChannelClosed`
（直接断 TCP）、`EOF => {}`，结果 pscp 数据全对、进度 100%，但**永远不退出**
（timeout 124）。OpenSSH 自己发 CLOSE，所以这个洞用 OpenSSH 测不出来。

现在 `closeChannel()` 先 EOF 再 CLOSE，`dispatch` / `waitForWindow` 的
EOF、CLOSE 四条路径都调它。

### 5. PuTTY 互通实测（第二套独立 SSH 栈）

`pscp -ls :/local`、下载 300 KiB、上传 —— 全部退出码 0 + md5 一致。
需要 `-hostkey SHA256:...`（batch 模式不确认 host key）。

> Windows 版 OpenSSH 的 `SSH_ASKPASS` 在本机 shell 里无效，口令认证无法
> 自动化 ⇒ OpenSSH 只验到 KEX+加密 USERAUTH；端到端靠 paramiko + PuTTY。

### 6. 调试口子

`openlist server --log-level debug` 会打每条 SSH 消息号（`ssh: msg N`）与
SFTP 包类型（`sftp: pkt xxx`）。「客户端卡在哪一步」就靠它定位。

### 8. 失败计数按 IP 分桶 —— 新增 `src/util/peeraddr.zig`

- 原来是**全局**一个计数：谁都能用错口令把管理员锁 5 分钟，还顺带锁住 HTTP
  登录（两边共用同一份计数是**特性**，换协议不该绕过限速）。根因是
  `std.Io.net.Stream` 不暴露对端地址。
- POSIX 用 `std.posix.getpeername`。**Windows 没有对应 API**：
  `std.posix.getpeername` 在 Windows 上 `@compileError("use std.Io instead")`，
  而 `Io/Threaded.zig` 的 `netAcceptWindows` 拿到了 `RemoteAddress` 却在构造
  `Socket` 时丢掉 ⇒ Windows 返回 null，回退全局桶，不假装支持。
- key **必须纯 IP 不带端口**（上游用 `IP:端口`，扫描器源端口每次都变 ⇒ 限速
  形同虚设）。不能拿 `Ip4Address.format` / `Ip6Address.format` 生成 key，两者
  都拼 `:端口`；`peeraddr` 自建 `format4`，IPv6 用 `Ip6Address.Unresolved.format`。
- IPv4 取字节必须按内存序 `@as(*const [4]u8, @ptrCast(&sin.addr)).*`，走 ntohl
  会把 `1.2.3.4` 变 `4.3.2.1`。
- 分桶：64 桶 + LRU。`ThrottleBucket` 加 `used: bool` —— **不能靠
  `key_len == 0` 判空闲**，全局桶的 key 本来就是空串。

### 9. 断点续传 + `READ` 不再把「驱动没报 size」当空文件

- 续传：`want_resume = !flags.trunc and exists`，`preloadExisting` 按
  `read_window` 分块把原内容拉进 temp（每块一个 arena）。上游短读**直接报错**，
  宁可失败也不能「上传成功但少一块」。失败路径是正常 `return`，`errdefer`
  不跑 ⇒ 手工 `free(vpath_owned)` + `destroy(st)`（漏了就是 2 处泄漏）。
- `details().size <= 0` 有两种含义（真空文件 / 驱动没报大小），原来一律当 0 ⇒
  `offset >= size` 恒回 EOF（「能列出来但读出来是空」）。加 `ReadState.size_known`：
  未知时不夹窗口，按 Range 实际返回判 EOF；`EndOfStream`/`OutOfRange` 映射 `.eof`。

### 10. 服务端主动 rekey（`sftp.rekey_mb`，默认 1024 MiB，0=关）+ 两个坑

- KEX 期间对端还在发 `CHANNEL_DATA`：新增 `ssh.Stash`（4 MiB / 256 条）暂存，
  NEWKEYS 后 `drainStash` 一包一个 arena 补投。等同于「这些包晚到了一点」。
- `-Osmall` 下 inferred error set 成环**直接链接失败**：
  `sendData → waitForWindow → onRekey → drainStash → dispatch → onChannelData →
  sendData`。给 `drainStash` 显式写 `anyerror!void` 断开。
- `Conn.init` **按值返回**，在 `init` 里取 `&self.stash` 存进 `Transport` 会
  悬垂（栈上副本）⇒ 必须在 `loop()` 开头再赋 `self.t.stash = &self.stash`。

### 11. host key 0600

写文件带 `Permissions.fromMode(0o600)`，**已存在的老文件也 tighten 一次**；
Windows 上 POSIX mode 无效，打 DEBUG 提示手工设 ACL。

### 12. ★ 端到端 15/15，但先踩了两个「测试自己写错」的坑

1. **paramiko 的 rekey 计数恒为 0**（看起来像服务端没 rekey，其实服务端日志里

2. **`--dir /local` 被 Git Bash 改写成 `C:/Users/.../PortableGit/local`**，

### 16. ★★ 互通脚本抓到的收尾缺陷：发完 EOF+CLOSE 就关 socket ⇒ 对端吃 RST

- 现象：psftp 连跑 15 次挂 6 次，两种报错交替（`Software caused connection
  abort` / `Remote side unexpectedly closed network connection`），而且**文件传完、
  rm 也 OK，就 quit 那一下报错**。
- 排除法：`--kib 64`（不触发 rekey）8/15 照样挂 ⇒ 与 rekey 无关；手工直连
  12 次挂 5 次 ⇒ 与脚本无关；两档数据量都挂 ⇒ 与大小无关。
- 根因：收到 `CHANNEL_EOF` → 发 `EOF`+`CLOSE` → **立刻 return** → `run` 返回 →
  `stream.close()`。对端回的 `CLOSE` 还在接收缓冲里没读走，Winsock 对「有未读
  数据的 close」发 **RST 而不是 FIN**。发不发 RST 取决于对端 CLOSE 有没有先到
  ⇒ 随机，所以以前偶发一次被当成环境抖动。
- 修法（RFC 4254 §5.3 关闭是双向握手）：收到 EOF 只发收尾包**不返回**，继续读；
  之后只认对端 `CLOSE`/`DISCONNECT`，其它包丢弃（上限 256 条兜底）；收到 CLOSE
  才返回。`closeChannel()` 改幂等（`closing` 标志），避免回两个 CLOSE。
- 验证：512 KiB ×15 = 0 失败（前 6/15）；64 KiB ×15 = 0 失败（前 8/15）；
  pscp 上传/下载 rc=0 + MD5 一致且不挂（它正是「只发 EOF 就等我们关」的客户端，
  最容易被新逻辑等死）；paramiko 端到端仍 15/15。
- ⚠ 又一个假通过的坑：`timeout 30 env MSYS_NO_PATHCONV=1 pscp …` 在 Git Bash 下
  **静默什么都不做**（rc=0、零输出、文件没传）。差点据此写「pscp 正常」。
  直接跑、不套 `timeout`/`env` 才对。
- 另：`tools/sftp_interop.py` 加 `--kib`；一开始写成
  `bytes(range(256)) * (kib//256 + 1)`，512 KiB 实际只生成 768 B —— 那两轮
  「0 失败」是在 768 字节上跑的，等于没测。加 `assert` 钉死长度后重跑才是真的。

## 21. 补验「服务端主动 rekey + 第三方客户端」⇒ 抓到 R10

配置 `sftp.rekey_mb = 1`（1 MiB）起实例，`tools/sftp_interop.py --kib 2048`：
WinSCP PASS，**psftp FAIL**（`Software caused connection abort`）。

服务端只有 `connection ended: TooManyPendingPackets`，两道上限共用一个错误码看不出哪个触发。
补诊断日志后：`items=256/256 bytes=1058304/4194304 incoming=4134` ⇒ **撞条数**。

根因：`Stash.max_items = 256` 的注释按「8 KiB 分片」估，而 **psftp 的 WRITE 是 ~4 KiB**，
2 MiB 在飞窗口要 ~512 条 ⇒ 只攒到 1 MiB 就断。以前测不出来是因为默认阈值 1024 MiB、
互通脚本只跑 512 KiB；paramiko 的 client-initiated rekey 里客户端已停发，stash 是空的。
