# 2026-11-01

## SFTP：客户端 rekey + 第二个客户端实现（PuTTY）+ 两处收尾缺陷

接着 10-31 的 SFTP 收尾，做掉 TODO 里剩的 `TODO(rekey)` 与「互通待测」。

### 1. 客户端主动重协商（rekey）

- `ssh.kex` 拆成 `kexInner(t, host_key, alloc, pending_client_kexinit)`：
  `kex` 传 null（首次），`rekey` 传消息循环已读到的那份 KEXINIT。
- `channel.Conn` 新增 `host_key` 字段（`Conn.init` 多一个参数），
  `dispatch` 与 `waitForWindow` 两处都接 `MSG_KEXINIT → onRekey(p)`。
- 三个必须对的点：`session_id` 沿用首次 H（§7.2）；`seq_in/seq_out` 不重置
  （§7.3）；**重协商用连接级 allocator 而不是循环的 arena**（kex 会把双方
  KEXINIT dup 进 Transport，下次还要用；arena 下一轮就释放 ⇒ 悬垂）。
  连做两次 rekey 才能抓到这条。
- 验证：paramiko `Transport.renegotiate_keys()` 连做两次，之后 300 KiB get
  仍逐字节一致。

### 2. `readPacket` 的返回值不能 `free`

- 返回的是 `body[1..len-padlen]`（分配起点 +5、长度不同），直接 `a.free(p)`
  会被 `SafeAllocator` 判成非法释放 **panic**。
- 新增 `Transport.readPacketOwned` → `OwnedPacket{raw, payload}`，
  `deinit` 释放 `raw`；`readPacket` 变成薄包装（arena 调用方不用管）。
  `readKexPacket` 返回 `OwnedPacket`，KEX 三处读包点各 `defer deinit`。
  顺带补上「KEX 期间跳过 IGNORE/DEBUG/UNIMPLEMENTED、DISCONNECT 当即断开」。

### 3. 协商失败发 DISCONNECT（不再静默关 socket）

`checkKexInit` 失败 → `Transport.rejectKex` 发 §11.1 的 `DISCONNECT`：
算法不匹配 = 3（描述里写清支持什么），KEXINIT 解析失败 = 2。
原因码常量放在 ssh.zig 顶部（`DISCONNECT_PROTOCOL_ERROR` 等）。

### 4. ★ 收尾：收到 `CHANNEL_EOF` 必须由服务端回 `EOF` + `CLOSE`

**PuTTY 的 pscp 传完只发一个 EOF 就等服务端关**（RFC 4254 §5.3：EOF 不要求
回应，结束靠 CLOSE）。原来 `CHANNEL_CLOSE => return error.ChannelClosed`
（直接断 TCP）、`EOF => {}`，结果 pscp 数据全对、进度 100%，但**永远不退出**
（timeout 124）。OpenSSH 自己发 CLOSE，所以这个洞用 OpenSSH 测不出来。

现在 `closeChannel()` 先 EOF 再 CLOSE，`dispatch` / `waitForWindow` 的
EOF、CLOSE 四条路径都调它。

### 5. PuTTY 互通实测（第二套独立 SSH 栈）

`pscp -ls :/local`、下载 300 KiB、上传 —— 全部退出码 0 + md5 一致。
需要 `-hostkey SHA256:...`（batch 模式不确认 host key）。

> Windows 版 OpenSSH 的 `SSH_ASKPASS` 在本机 shell 里无效，口令认证无法
> 自动化 ⇒ OpenSSH 只验到 KEX+加密 USERAUTH；端到端靠 paramiko + PuTTY。

### 6. 调试口子

`openlist server --log-level debug` 会打每条 SSH 消息号（`ssh: msg N`）与
SFTP 包类型（`sftp: pkt xxx`）。「客户端卡在哪一步」就靠它定位。
