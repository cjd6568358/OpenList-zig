## CI「裁剪」镜像体积之谜（2026-10-18 深夜排查，用户提问）

**现象**：workflow 产出的「CDN + 裁剪驱动」sqfs 镜像（Release `ci-sqfs-296c3cb`，
资产 `openlist.sqfs_`，20.3 MB）与光猫现役全量 Go 镜像
（`/opt/armbian/bin/openlist/openlist.sqfs` = 21,155,840 B，二进制 88.5 MB，含前端）
体积一致。

**根因**：该 run 是 **push 触发**（296c3cb6 → feat/zhijiadisk），不是
workflow_dispatch。GitHub 的 `inputs` 上下文只在 dispatch/call 时填充，push 时
`${{ inputs.* }}` 全为空串 —— workflow 里写的 `default:`（11 驱动、strip_*=true、
db=sqlite、arch=linux-arm64）只对手动触发生效。连锁后果：
- `--drivers ""` → gen_overlay.py 的 `parse_list("")` 返回 None ≡ "keep all"
  → **87 个驱动全编入**；
- `[ "" = "true" ]` 不成立 → strip_offline / strip_ffmpeg **都没剥**；
- `--db-backends ""` → None → mysql/postgres 没摘；search 同理；
- `arch` 空 → `case "$TARGET"` 全落空 → GOOS/GOARCH 不设 → ubuntu-latest(x86_64)
  上编出 **linux/amd64** 二进制（上设备也跑不了）。
铁证：资产名 `openlist.sqfs_`（模板 `openlist.sqfs_${TARGET}` 后缀空）、release
notes 每个字段全空、同 run `ci-296c3cb` 明写"触发: push / 分支: feat/zhijiadisk"。
CI 全绿是因为没有任何步骤断言 arch 或"裁剪真的发生了"。

**附带发现（Zig workflow 独立 bug）**：`build_zig_minimal.yml` 所有 `zig build`
都在仓库根执行，根目录没有 build.zig（在 zig-src/）→ "Show build.zig options"
步骤即失败 ⇒ **该 workflow 从未产出过任何镜像**。需给相关步骤加
`working-directory: zig-src`；其 drivers 默认空串=全量，与 Go 版默认 11 驱动不一致。

**修复方向**（未动手）：Go 版 env 加兜底 `${{ inputs.arch || 'linux-arm64' }}`
等，或 arch 为空直接 ::error:: 硬失败（静默 amd64 最危险）。

## 勘误 + 新事故（koofr 429 真相：不是限流，是登录锁定）

上文「koofr 限流铁律」结论**作废**。带 `-i` 重看 429 响应体：
**`Too many login retries`** —— 是**账号登录锁定**，不是流量限流。

- 肇因：我写 hammer 探针时凭据提取有 bug（busybox awk `split` 的分隔符
  `","` 与 cfg.json 原文的 `\",\"` 不匹配），**发出 5 次错误密码 401**，
  触发 koofr 锁定；此后一切带凭据请求 429，无凭据请求仍只回 401（不受
  影响）—— 这就是「登录锁定 vs 流量限流」的识别判据。
- 锁定 ≥70 分钟未退，且**每次认证尝试都可能重置计时器**：我每 3 分钟的
  轮询探针（fs/list → PROPFIND 带凭据）一直在**续锁**，已停。
- 教训（已写进 MEMORY.md 铁律）：① 对第三方网盘发批量请求前，探针必须
  先用**已知正确凭据**打阳性对照；② busybox awk 无区间量词，提取 JSON
  字符串值用 `index`+`substr`+`sub` 纯字符串操作；③ 429 先看响应体再
  下结论。
- 现状：koofr 挂载点在本轮最终回归里无法验证（账号锁），已彻底停碰，
  锁定期过后补跑。除此之外 115 段全绿、/115 残留已清空。

## 翻案：115 下载 403 是本端真 bug（WebDAV 漏传请求头）

**怎么翻的**：给「Go 同结果」这个演绎结论补对照组 —— 设备上起一个只挂 115 的
**Go 实例**（/opt/sq/openlist/openlist，端口 15398，/tmp/goab 独立空库），
同文件同秒同 UA 各取一次：**Go 200（38B 正文）/ Zig 403**。演绎结论当场证伪。

**受控实验**：115 直链签名 **绑定 User-Agent** —— 同 UA 取 200、换 UA 取 403
（Go/Zig 两侧生成的 URL 结构完全一致）。所以两侧「生成」都对，差在「回源请求」。

**根因**：`src/webdav.zig` 三处 `driver.link(...)` 只传 `.redirect`，**没传
`.headers`**；Go 的 webdav.go:257/:274 都传 `Header: r.Header`。⇒ 115 驱动拿空
UA 签 → 回源 UA 不一致 → 恒 403。（`/d/` 与 `fs/get` 本来就传了，所以同实例
`/d/` 一直 200、只有 WebDAV 403 —— 这条差异是定案关键。）

**修复**：webdav.zig 三处 + api.zig archive 补 `.headers = req.headers`；
**撤掉** e2e 里上一轮给 115 开的 403 豁免（基于错误结论的豁免会掩盖真 bug）。

**验证**：407/407 单测；WebDAV GET 200/38B、Range 206 + Content-Range、
/d/ 200；全量 e2e **430 过 / 0 败 / 1 跳**（仅坚果云根级删 403）。
产物 sha256 `62071006d75a…`。koofr 账号锁也已自愈（单点 74/0/0）。

**教训（已进 MEMORY.md）**：证据链自洽 ≠ 结论正确；「URL 相同 ≠ 请求相同」；
凡调 driver.link 必须传 .headers。
