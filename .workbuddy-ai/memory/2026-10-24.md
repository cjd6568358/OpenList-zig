### ② `sign invalid`：已定位并修复（真 bug，真机验证）

- 现象：`[WARN] [api] /d/ sign rejected for /ecloud_self/我的音乐/Trouble Is A
  Friend.mp3: SignInvalid` —— 自己签的名自己验不过。
- **根因**：请求路径解码用了 **form 语义**。`util/url.zig:decode` 无条件把 `+`
  当空格，而 `http.zig` 的 `req.path` 正是用它解的。真实文件名是
  `Trouble+Is+A+Friend.mp3` ⇒ 签名算在带 `+` 的路径上，验签却拿折成空格的路径
  比 ⇒ HMAC 不等。Go 天然正确：`net/url` 解 `URL.Path` 用 `unescape(encodePath)`
  （不认 `+`），只有 `Query()` 用 `+`→空格 的 `QueryUnescape`。
  `sign_all=false` 后同一处错位往下走一层，表现成 `object not found`（500）。
- 修复：新增 `util/url.zig:decodePath`（保留 `+`），`decode` 保留给查询串；
  `http.zig` 抽出 `pub fn decodeRequestPath` 供 `readRequest` 与测试共用；
  `webdav.zig:destVpath`、`drivers/webdav.zig` 的 PROPFIND `<href>` 同样改
  `decodePath`。
- 测试（+3）：`decodePath` 保留 `+` 且与 `.path` 编码互逆；`decodeRequestPath`
  三条；api 层"带 `+` 的路径签得出来就验得过"+折成空格必须 SignInvalid。

### ④ sign_all 与 Strm 驱动的关系（用户追问，已查证：不冲突）

- Strm 的 Addition 有 **`withSign`**（Go `drivers/strm/meta.go:23`，Zig
  `strm.zig:52` `with_sign`）。打开后生成的 .strm 内容自动拼
  `?sign=<签名>`（Go `util.go:114-116`，Zig `strm.zig:454-460`）。
- 关键点：这个签名走 `bridgeSign` = `signValue(secret, path, 0)`，**expire=0
  永不过期**，对齐 Go `sign.Sign(path)`；**不受 `link_expiration` 影响**。
  所以 sign_all=true + withSign=true 时 .strm 里的直链能长期用。
- 前提：`sign.Sign` 签的是**未编码的原始媒体路径**，/d/ 验的是**解码后的请求
  路径** —— 在 `+` 修复之前这两边对不上，带 `+` 的文件即便开了 withSign 也会被
  自己拒（同一个 bug 的另一张脸）。修完才成立。
- 现网 storage #22 的 addition **只有 `paths`**（`/ecloud_self/我的音乐`），
  `withSign`/`siteUrl` 都是默认；全局 `site_url` 为空 ⇒ 内容里的前缀按请求
  Host 拼（实测 `http://192.168.1.1:15244/d/...`）。`link_expiration`=0。
- 已落盘的旧 .strm 不会自动更新：`saveStrmToLocal` 开着时 `generateStrm`
  比对内容后重写（strm.zig:648）；手工写的要重新生成。

### ⑦ 与上游逐句对账（用户要求"别自己改逻辑，你只是 Zig 重写"）

**结论：`+` 的修复是对齐上游，不是发明。** 上游链路里没有任何一环折 `+`：
- gin 未设 `UseRawPath`（全树无此符号）⇒ `c.Param("path")` 取自
  `req.URL.Path`，由 `net/url` 用 `unescape(encodePath)` 解码，**不认 `+`**；
- `middlewares.PathParse` → `utils.FixAndCleanPath`（pkg/utils/path.go:19-25）
  只做 `\`→`/`、补前导 `/`、`stdpath.Clean`，**不碰 `+`**；
- 全树 `QueryUnescape`/`PathUnescape` 只出现在 drivers 内部（123_link/139/
  189/bunny/guangyapan/onedrive/gowebdav），**不在 HTTP 下载链路上**，且
  `PathUnescape` 本身也不折 `+`；
- 唯一折 `+` 的地方是 `c.Query("sign")`（`QueryUnescape`，查询语义）——
  Zig 的 `queryGetDecoded` 保留了这个行为，两者一致。

对账发现的**既有偏差**（均非本次引入，未改，等用户定夺）：

| # | 上游 | Zig 现状 | 严重度 |
|---|---|---|---|
| D1 | `PathParse` 对 `/d/*path` 做 `FixAndCleanPath`（`\`→`/`+`Clean`） | `handleDownload` 只 `"/" + raw`，**没做**；但 Zig 已有忠实实现 `normalizeMountPath`（api.zig:327，注释明写对齐 FixAndCleanPath），只是 /d/ 没用上 | 中 |
| D2 | fs/get 的 raw_url 条件 = `storage.Config().MustProxy() \|\| storage.WebProxy`（server/common/check.go:106-113），且**先试** `GenerateDownProxyURL`（DownProxyURL） | 条件是 `lk.proxy or lk.local_path != null`，**无** DownProxyURL 分支 | 中 |
| D3 | raw_url = `GetApiUrl(c) + "/p" + EncodePath(reqPath,true)`（**绝对** URL） | 相对 `/p...` | 低 |
| D4 | `EncodePath(p,true)` = 每段 `url.PathEscape`，只放过 字母数字 `-_.~$&+:=@` | fs/get 用 `util/url.zig` 的 `.path`，多放过 `! ' ( ) * , ;`；**但 `strm.zig:pathEscape`（Strm 用）是忠实的** | 低 |

签名算法本体对账**全对**：`HMACSign.Sign` =
`base64.URLEncoding(hmac(secret, data+":"+exp)) + ":" + exp`
（pkg/sign/hmac.go:20-30），密钥 = `setting.GetStr(conf.Token)`
（internal/sign/sign.go:37）；Zig `signValue` 用 `url_safe`（带 padding）+
`signKey`=`zig.token`，一致。唯一差异：Zig 用常量时间 `ctEqual` 取代 Go 的
`!=`，语义等价且更安全，属刻意。
