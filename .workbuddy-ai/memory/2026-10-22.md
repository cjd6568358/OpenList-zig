## 17:05 itvsh access_token 审计结论（用户质疑"为什么老是回写"）

- **Go 也落盘**：`drivers/itvsh/meta.go:14` 是 `json:"access_token"`，
  `Drop()` 还会 `MustSaveDriverStorage(d)`；`driver.go:47` 的注释明确写着
  "AccessToken（用户填的配置，带 json tag、会落库）"。
- **登录产物两边都只存内存**：Go `sessionToken`（无 json tag）、Zig `session_token`
  （itvsh.zig:225 注释 + login 只写内存）。所以"程序把登录 token 写进配置"这条路不存在。
- 那 10-16 备份里那枚 32 位 hex 的 `access_token` 是**外部来源**（用户手填或旧版本写入），
  一旦在里面就永远优先、永远失效 —— 这才是"老是回写"的观感。
- **发现一个真实漏洞（未修，待定）**：`main.zig:persistStorage` 无条件用驱动传来的
  addition 覆盖配置，不校验调用者是不是"当前活着的那一个驱动实例"。`storage/update`
  后旧实例**不 deinit**（留给在途请求），它若此时 persist（itvsh 的 saveCookies/relogin、
  wopan 的 save），会把**旧 addition（含旧 token）**盖回去 —— 对一次性令牌驱动等于丢令牌。
- 本轮两次"token 又回来了"其实是**我自己的操作错误**：① 改 cfg.json 没先停实例；
  ② 改了内存 dict 却上传了原始文件。
